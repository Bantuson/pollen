# Pollen Supply-Chain Threat Model

**Version:** v0.1.1-pollen.1
**Date:** 2026-06-01
**Status:** Published (Phase 1 — fork-setup-discipline)

This document describes the supply-chain security properties of the Pollen
binary, the threats it faces as a fork of upstream `perplexityai/bumblebee`,
and the verification path an operator uses to confirm binary integrity.
It is scoped to the supply-chain surface introduced in Phase 1 (FORK-03).

## 1. What Pollen Is and Its Supply-Chain Position

Pollen is a Go fork of `perplexityai/bumblebee` (v0.1.1) at pinned commit
`c24089804ee66ece4bec6f14638cb98985389cdb`. It is a standalone CLI tool that
scans package manifests for known-malicious packages. Beekeeper depends on
Pollen as a scan provider.

### Supply-Chain Position

```
upstream bumblebee v0.1.1 (pinned SHA)
         │
         ▼
    pollen fork  ─── built by GitHub Actions ───► signed release artifact
         │                                              │
         │                          cosign keyless ───►│
         │                          SLSA L3 provenance ►│
         │                          CycloneDX SBOM ────►│
         ▼
    beekeeper (pins pollen at explicit version)
```

Pollen sits between upstream bumblebee (unreviewed code absorbed at the
pinned SHA) and Beekeeper (the safety harness that depends on pollen). Both
trust boundaries are live: pollen absorbs upstream code, and beekeeper
trusts pollen release artifacts.

## 2. Supply-Chain Threats and Mitigations

### Threat 1: Unreviewed Upstream Code Absorption

**Description:** When pollen forks or syncs upstream bumblebee, it absorbs
code that has not been fully audited. A malicious or compromised upstream
commit could introduce backdoors, exfiltration logic, or behavioral changes
that affect pollen's scan accuracy.

**STRIDE:** Tampering (T-01-10)

**Mitigations:**
- **Pinned SHA**: pollen is pinned to a specific commit
  (`c24089804ee66ece4bec6f14638cb98985389cdb`), not to a floating branch.
  Upstream main has diverged (6+ commits since v0.1.1); none are absorbed
  until a deliberate sync.
- **Diff review before absorption**: every upstream sync requires a manual
  diff review (UPSTREAM.md sync workflow). No auto-absorption of upstream main.
- **Deferred sync**: upstream integration is gated to Phase 5 (SYNC-01/SYNC-02)
  — not opportunistic.
- **Differential test guard**: `TestDifferential` (locked name in
  `cmd/pollen/differential_test.go`) asserts pollen produces byte-identical
  normalized NDJSON to upstream bumblebee on a fixed fixture. Any behavioral
  divergence introduced by an upstream sync will trip this test in CI.

**Residual risk:** Code at the pinned SHA has not been exhaustively audited.
Pollen is zero-external-dependency (no `go.sum`), so transitive supply-chain
risk is confined to the Go stdlib and the upstream code itself.

### Threat 2: Compromised Pollen Release Pipeline

**Description:** An attacker who compromises the GitHub Actions runner, steals
an OIDC token, or gains write access to the `bantuson/pollen` repository could
sign a malicious release artifact — making it appear legitimate to operators.

**STRIDE:** Spoofing, Tampering, Elevation of Privilege (T-01-13)

**Mitigations:**

**2a. Keyless Signing (no long-lived key to steal)**
Pollen uses cosign v3 keyless OIDC signing. There is no private signing key
stored anywhere — the signing identity is bound to the GitHub Actions workflow
at release time via the OIDC token:
```
https://github.com/bantuson/pollen/.github/workflows/release.yml@refs/tags/v...
```
An attacker who cannot trigger the release workflow cannot produce a valid
signature. Stealing a developer's machine credentials does not yield a signing key.

**2b. Reproducible Builds (builds can be independently re-derived)**
Every release binary is built with:
```
-trimpath -buildvcs=false -mod=readonly
```
These flags ensure two independent builds from the same tagged source produce
byte-identical output. An operator can verify locally:
```bash
make verify-release VERSION=0.1.1-pollen.1
```

**2c. SLSA Level 3 Provenance (build environment attestation)**
Release provenance is generated by `slsa-github-generator@v2.1.0` (full
semver — pinning to `@v2` alone is insufficient for SLSA Level 3). SLSA L3
guarantees:
- The build was triggered by a source commit the attacker cannot forge
  without write access to `bantuson/pollen`.
- The build environment was ephemeral and unmodified by the build script.
- The provenance is signed by the SLSA generator, not by the project itself.

**2d. Two-Account Release Approval Discipline**
Tag-push authority controls release pipeline triggering. Release approval
policy (enforced in plan 05) requires a second GitHub account to approve
before pushing a release tag. A single-account compromise cannot silently
push a malicious release tag.

### Threat 3: Pollen as a Beekeeper Supply-Chain Link

**Description:** Beekeeper depends on pollen. If pollen releases a compromised
binary, Beekeeper's scan results are poisoned — an agent could install malicious
packages that pollen's scan misses or approves.

**STRIDE:** Tampering, Repudiation (T-01-14)

**Mitigations:**
- Beekeeper pins pollen at an **explicit, reviewed version** (not a floating
  "latest"). A pollen release cannot silently change Beekeeper's behavior
  without a deliberate version bump in Beekeeper.
- The Sigstore transparency log records every pollen release signature in an
  append-only log. Post-hoc detection of a malicious release is possible.
- The CycloneDX SBOM (SDEF-02) records the pinned upstream commit
  (`c24089804ee66ece4bec6f14638cb98985389cdb`) in every pollen release artifact.
  This allows auditors to determine exactly what upstream code each release is
  based on.

**Deferred — pollen-self catalog (SDEF-01):** The recursive self-defense
mechanism — a `pollen-self` catalog entry in beekeeper's threat intel that
would flag a compromised pollen version — is out of scope for Phase 1. It is
scheduled for Phase 5 (SDEF-01). Until SDEF-01 ships, beekeeper does not
have automatic self-quarantine for a compromised pollen dependency. Operators
should monitor the Sigstore transparency log for unexpected pollen signatures
in the interim.

---

### Threat 4: Reproducibility Regression from Missing `-buildvcs=false`

**Description:** Upstream's `goreleaser.yaml` lacks `-buildvcs=false`. If
pollen's release configuration regresses to upstream's (e.g., during an upstream
sync that overwrites the goreleaser file), builds will embed VCS state
(commit hash, dirty status) that varies between machines, breaking reproducibility.

**STRIDE:** Tampering (T-01-15)

**Mitigations:**
- Both `Makefile` and `.goreleaser.yaml` explicitly set `-buildvcs=false`.
- `verify-release` double-build hash comparison catches any reproducibility
  regression before a tag is pushed.
- The differential test and SLSA provenance gate run on every CI push —
  providing independent confirmation that the build is correct.

---

### Threat 5: Wrong cosign Identity Regexp

**Description:** The `--certificate-identity-regexp` in the operator verify
command (see Section 3) could be wrong if the GitHub Actions OIDC cert
identity format differs from the assumed
`https://github.com/bantuson/pollen/...` shape.

**STRIDE:** Spoofing (T-01-16) — Accepted

**Rationale for acceptance:** The regexp is anchored to
`^https://github.com/bantuson/pollen/` which is the standard GitHub Actions
OIDC identity format (verified against beekeeper's identity pattern). The
exact URL in the sigstore certificate will be validated after the first actual
release (plan 05 checkpoint, Assumption A1 from 01-RESEARCH.md). Until then,
the regexp is documented as provisional.

**Action at plan 05:** After pushing the `v0.1.1-pollen.1` tag and observing
the sigstore bundle, confirm the actual identity URL matches the regexp and
update this document if needed.

## 3. Verification Path (Operator)

Use this path to verify a pollen binary before use, or to investigate a
potentially tampered artifact.

### Step 1: Verify the cosign signature (OIDC-only trust, no long-lived key)

Download `checksums.txt` and `checksums.txt.sigstore.json` from the release,
then verify:

```bash
cosign verify-blob \
  --bundle checksums.txt.sigstore.json \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-identity-regexp "^https://github\.com/bantuson/pollen/" \
  checksums.txt
```

A successful verification confirms:
- `checksums.txt` was signed by a GitHub Actions OIDC token bound to the
  `bantuson/pollen` repository.
- No long-lived signing key was used.
- The signer's identity is `github.com/bantuson/pollen` (not an unrelated
  workflow).

**Note (Assumption A1):** The exact identity URL in the sigstore certificate
is validated after the first release (plan 05). The regexp
`^https://github\.com/bantuson/pollen/` is anchored to the correct namespace
and will catch any non-pollen signer.

### Step 2: Verify SLSA Level 3 provenance

```bash
slsa-verifier verify-artifact pollen \
  --provenance-path pollen.intoto.jsonl \
  --source-uri github.com/bantuson/pollen
```

SLSA L3 provenance confirms the build environment was ephemeral, the build
was triggered by a signed commit, and the provenance was produced by the SLSA
generator (not the project's own workflow).

### Step 3: Verify reproducibility locally

```bash
make verify-release VERSION=0.1.1-pollen.1
```

This builds pollen twice from source with identical flags and compares sha256
hashes. A mismatch indicates the released binary was not produced from the
tagged source, or the build environment differs (e.g., different Go toolchain
version — see Makefile header for toolchain requirements).

### Step 4: Inspect the CycloneDX SBOM

```bash
# The SBOM records the upstream commit this release is based on:
cat pollen-*.cdx.json | jq '.metadata.component.properties[] | select(.name=="upstream-commit")'
# List all Go dependencies (should be stdlib-only for v0.1.1-pollen.1):
cat pollen-*.cdx.json | jq '.components[].name' 2>/dev/null || echo "(no external components — stdlib only)"
```

The SBOM for `v0.1.1-pollen.1` records upstream commit
`c24089804ee66ece4bec6f14638cb98985389cdb` as the source, satisfying the
SDEF-02 provenance requirement.

## 4. Known Gaps and Deferred Items

### pollen-self catalog (SDEF-01) — deferred to Phase 5

The recursive self-defense mechanism — a `pollen-self` catalog entry in
beekeeper's threat intel that would flag a compromised pollen version at
runtime — is **out of scope for Phase 1**. It is scheduled for Phase 5
(SDEF-01, milestone v0.1.1-pollen.5).

Until SDEF-01 ships:
- Beekeeper pins pollen at an explicit version (no automatic update).
- The Sigstore transparency log is the available audit trail for pollen
  release signatures.
- Operators monitoring beekeeper should watch the pollen release feed and
  verify signatures manually for high-security environments.

This gap is explicitly documented here because pretending it does not exist
would be dishonest.

### Single-maintainer governance (for v0.1.1-pollen.1)

For `v0.1.1-pollen.1`, the pollen release signing and tag-push authority is
held by a single maintainer (Bantuson — `github.com/bantuson`). An attacker
who compromises this account can produce a signed release.

**Intent for post-v0.2.0:** Separate release-tag approval from the committer
identity; require a second GitHub account to approve the release tag push
(enforced in plan 05 for v0.1.1-pollen.1 as a process discipline).

### Assumption A1 — cosign identity string shape

The `--certificate-identity-regexp` in the verify command above uses
`^https://github\.com/bantuson/pollen/` based on the standard GitHub Actions
OIDC identity format. The exact URL in the first real release's sigstore
certificate will be inspected during plan 05 and this document updated if
the pattern differs.
